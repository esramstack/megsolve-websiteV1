CASE STUDY &middot; SOFTWARE DEVELOPMENT

Large datasets that actually stay usable.

Rebuilding the data-heavy screens of a Pakistani POS platform around AG Grid, so large catalogues and transaction histories stayed workable in the browser.

Client
POS Platform, Pakistan
Engagement
Software Development
Hosting
AWS
Scope
Data Interface

The opportunity

01 · CONTEXT

Retail operators work in tables. Product catalogues, transaction histories, stock movements, and sales reports are all fundamentally grids, and on this platform those grids had outgrown the components rendering them.

Loading full datasets into the browser meant slow initial renders, sluggish scrolling, and filtering that operated on whatever subset happened to be loaded rather than the whole set. The larger a client's catalogue, the worse their experience.

The requirement was a data layer that behaved the same at ten thousand rows as at one hundred.

The solution

02 · DELIVERY

AG Grid adopted as the standard data component, with the heavy lifting moved from the browser to the server.

PH 01

Server-side data model

  • Paging, sorting, and filtering moved server-side so the browser holds only the visible window
  • Row virtualisation applied so scroll performance stays constant regardless of dataset size
  • API contracts defined between grid state and backend query parameters
PH 02

Interaction and usability

  • Column-level filtering and multi-column sorting exposed to end users
  • Grouping and aggregation enabled for reporting views
  • Column visibility, ordering, and sizing made adjustable and persistent per user
PH 03

Reporting and export

  • CSV and Excel export wired to the full filtered dataset rather than the loaded page
  • Custom cell rendering applied for status indicators, currency, and inline actions
  • Consistent grid behaviour standardised across every data screen in the product

The impact

03 · OUTCOME

Consistent performance at scale

  • Screen responsiveness decoupled from dataset size
  • Large-catalogue clients no longer penalised for having more data

Better operator workflow

  • Filtering and sorting applied across complete datasets rather than loaded subsets
  • Export reflecting exactly what the operator had filtered on screen
AG GridServer-Side Row ModelRow VirtualisationAWSCSV and Excel Export
CLOSING NOTE

The fix was architectural rather than cosmetic: stop sending the whole dataset to the browser and the performance problem stops being a performance problem.
